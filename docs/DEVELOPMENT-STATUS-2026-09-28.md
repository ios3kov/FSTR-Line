## Текущий этап — порядок очереди и связь проектов

База этого шага: `c8431386d2dc123e85f6c0c78cee621e31037f83`.
Правила main: blob `701a8c1ae3acb4dbfe1d7eda94acbf8095b88608`, без изменений.

Получен и разобран новый `FSTR-AE-Queue-qk6xsvhj`: все 19 запрошенных тел,
26 успешных команд, 5 029 последовательных четырёхбайтовых позиций. Проверены
контрольные суммы и связь с неизменённым пакетом `eef15f5`. Это нужный новый
отчёт; повторный сбор тех же функций не требуется.

Установлено по коду конкретной сборки AE:

- Команды добавляются в конец очереди и извлекаются с начала под блокировкой.
  Вызов происходит уже после удаления команды и снятия блокировки. Глобальный
  порядок завершения и единственный поток исполнения этим ещё не доказаны.
- Отмена может очистить очередь. Счётчик обработки не является подтверждением
  успешной доставки каждой команды. Проверка идентификатора проекта в этом
  обработчике выполняется после вызова, а не защищает его заранее.
- Основной проект, clone и faux имеют отдельные пути создания и хранения.
  Полная десериализация направляется в clone. Сырые указатели из getters не
  дают внешнему клиенту подтверждённого владения или безопасного времени жизни.
- RegisterListener хранит callback в отдельной структуре. Её связь с очередью
  обновления проекта и безопасный контракт внешней подписки пока не установлены.

Все 50 строк `.long` дополнительно декодированы локальным LLVM. Четыре байта
таблицы переходов CommandType в отчёте отсутствуют: нельзя приписывать generic
callback ветку пропуска при загрузке только по соседним инструкциям.

Решение: эту очередь нельзя считать самостоятельным надёжным каналом
уведомлений о зафиксированном UI-состоянии. Возможная комбинация каналов
требует отдельного доказательства. Production-код и сборщик не изменялись.

## Незакрытые условия и следующий шаг

**SYNC-001: production integration BLOCKED/NOT RUN.** Следующие конкретные
пробелы: вызывающая сторона и назначение потока для callback очереди `+0x40`;
контракты BEE_QueryProject / BEE_GetCurrentConstProject / BEE_ProjectSetContext;
таблица переходов CommandType; emitter и время жизни WorkQueue-подписчика.
Дальнейший сбор должен закрывать эти пробелы, не повторять прежний отчёт.

Настоящие поток/порядок выполнения, соответствие активному UI-проекту,
безопасная подписка и снятие подписки, post-commit доставка, пропуски/повторы,
закрытая панель и нагрузка без отладчика ещё не приняты. Native harness допустим
только после установления безопасных контрактов. LLDB/polling/idle/focus/
self-events не заменяют источник уведомлений. Issue #3 о таймауте завершения
исследовательского LLDB остаётся открытой.
