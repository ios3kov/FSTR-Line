# Development Rules

Эти правила применяются ко всем инструментам для Adobe After Effects:

- native plugins / effects (`.plugin`, `.aex`);
- scripts (`.jsx`, `.jsxbin`);
- ScriptUI panels;
- CEP extensions;
- UXP plugins / panels;
- вспомогательным приложениям и helper-процессам;
- пакетам из нескольких компонентов.

---

## 1. Перед каждым шагом

Перед началом любого этапа разработки сверяться с этим документом.

---

## 2. Чистое тестирование

Каждый финальный, regression- и bug-reproduction тест в After Effects должен запускаться с чистого состояния.

Не должно оставаться:

- старых сборок;
- старых версий скриптов или extensions;
- старых установленных копий инструмента;
- кэшей, способных повлиять на результат;
- временных файлов;
- старого состояния, которое искажает тест;
- следов предыдущих тестов.

Для panel / script / CEP / UXP дополнительно учитывать:

- сохранённое состояние;
- preferences;
- локальное хранилище;
- CEP/UXP/ExtendScript cache;
- старые event listeners;
- timers / polling;
- background/helper processes;
- необходимость перезапуска After Effects.

Новый тест не должен случайно использовать старый artifact или старое состояние.

Для быстрых внутренних итераций допускается сокращённый цикл, если это не влияет на достоверность результата.

Финальная проверка всегда проводится на чистом состоянии.

---

## 3. Research перед разработкой

Перед написанием новой функции сначала проверить:

- Adobe SDK и официальную документацию;
- After Effects scripting API;
- CEP / UXP документацию, если применимо;
- существующие решения;
- open-source;
- похожие плагины;
- похожие scripts / panels / extensions;
- готовые проверенные подходы;
- известные ограничения After Effects.

Если хорошее решение уже существует — адаптировать его, а не писать заново.

Не изобретать собственный механизм без необходимости, если существует проверенный стандартный способ.

---

## 4. Максимальная автоматизация

Всё, что можно сделать без участия пользователя, делать автоматически.

Не просить пользователя:

- запускать проверки;
- собирать данные;
- искать логи;
- очищать кэш;
- копировать файлы;
- устанавливать сборки;
- выполнять технические операции;
- тестировать промежуточные гипотезы,

если это можно сделать самостоятельно.

### Автоматизация After Effects

Где технически возможно, использовать автоматический запуск After Effects для smoke / integration tests.

Для ExtendScript / JSX могут использоваться:

- автоматический запуск `.jsx` через поддерживаемый command-line запуск After Effects;
- `afterfx -r path/to/test_runner.jsx`, где это поддерживается целевой платформой/версией;
- собственный test runner внутри After Effects.

Для render-specific сценариев использовать:

- `aerender`;
- подготовленные test projects;
- автоматическое сравнение render output.

`afterfx -r` не считать полноценным headless-режимом. Он используется как средство автоматического запуска скрипта в After Effects.

`aerender` использовать прежде всего для render automation, а не как универсальную замену scripting test runner.

Автоматические AE-тесты должны по возможности:

1. открывать подготовленный test project;
2. запускать тестируемую функцию;
3. сохранять результат;
4. записывать логи;
5. возвращать однозначный PASS / FAIL;
6. закрывать тестовое состояние без ручного участия пользователя.

Ручной тест пользователя — последний этап, а не часть процесса диагностики.

---

## 5. Максимальная скорость разработки

Всё независимое, что можно безопасно выполнять параллельно, выполнять параллельно:

- research;
- сборки;
- статический анализ;
- автоматические тесты;
- аудит;
- profiling;
- benchmark;
- документацию.

Параллельность не должна:

- снижать достоверность тестирования;
- создавать race conditions;
- смешивать результаты разных builds;
- приводить к тестированию устаревшего artifact.

---

## 6. Git обязателен

Любое изменение проходит через Git.

Каждый законченный этап:

- отдельное понятное изменение;
- понятный commit;
- возможность быстро откатиться.

Не смешивать несвязанные изменения в одном commit без необходимости.

Перед milestone / release / передачей пользователю рабочее дерево должно быть `clean`.

---

## 7. Build / Artifact Identity

### Термин Artifact

Artifact — конкретный результат разработки, который устанавливается, запускается или используется в After Effects.

Это может быть:

- `.plugin`;
- `.aex`;
- `.jsx`;
- `.jsxbin`;
- ScriptUI panel;
- CEP extension;
- UXP plugin;
- ZIP/package;
- helper executable;
- набор связанных файлов.

### Identity

Для каждого тестируемого artifact должно быть однозначно известно:

**Git commit + clean/dirty → Build ID → artifact → SHA-256 → установленная версия → реально загруженная версия в After Effects**

Build Identity должен содержать:

- Git commit;
- состояние `clean/dirty`;
- Build ID;
- версию инструмента;
- идентификатор типа artifact.

После создания artifact автоматически рассчитывается SHA-256.

Если artifact состоит из нескольких файлов:

- рассчитывать hash финального package/archive;

или

- создавать manifest с SHA-256 всех production-файлов.

Нельзя считать тест достоверным, если невозможно доказать, какая именно версия кода тестировалась.

### Перед ручным тестом пользователя обязательно убедиться, что:

- используется нужный commit;
- Git state `clean`;
- старые версии удалены;
- установлен именно новый artifact;
- After Effects загрузил именно его;
- версия однозначно определяется;
- SHA-256 соответствует проверенному artifact.

### Обязательная реализация Build Identity

Где технически возможно, Git commit / Build ID должны автоматически попадать внутрь инструмента.

Для native plugins:

- передавать данные через CMake / MSBuild / Xcode;
- показывать Build ID / commit через `PF_Cmd_ABOUT`;
- писать Build ID первой строкой лог-файла.

Для scripts / panels / CEP / UXP:

- хранить Build ID / commit в generated metadata;
- выводить его в About / Diagnostics;
- писать его в диагностический лог.

Build Identity не должен требовать ручного редактирования перед каждой сборкой.

Сборка со статусом `dirty` допустима для внутренних экспериментов, но:

- не может передаваться пользователю;
- не может считаться milestone;
- не может считаться release;
- не может быть финальным Evidence.

---

## 8. Baseline перед изменениями

Перед серьёзной правкой фиксировать текущее состояние.

### Для любого инструмента

- что работает;
- что не работает;
- известные ошибки;
- текущий artifact;
- Build ID;
- Git commit;
- время выполнения критичных операций;
- использование памяти.

### Для render/effect plugins

Дополнительно:

- Render performance;
- RAM Preview performance;
- CPU;
- GPU;
- MFR;
- cache behaviour;
- bit depth;
- color-management configuration.

### Для scripts / panels / extensions

Дополнительно:

- время запуска;
- время выполнения основных операций;
- UI responsiveness;
- host-call latency;
- file I/O;
- memory behaviour;
- поведение на больших проектах.

Это точка сравнения после изменений.

---

## 9. Regression Check — два уровня

### Level 1 — после каждого commit

Выполнять быстрые проверки:

- build / packaging;
- запуск;
- основные функции;
- smoke tests;
- отсутствие очевидных regressions;
- отсутствие новых ошибок;
- базовые performance sanity checks.

Для scripts без стадии компиляции под `build` понимается создание и проверка финального artifact/package.

### Level 2 — перед milestone / release / ручным тестом пользователя

Проводить полный regression:

- весь основной функционал;
- edge cases;
- error handling;
- повторный запуск операций;
- сохранение/восстановление состояния;
- restart After Effects;
- performance;
- память;
- совместимость;
- реальные тесты внутри After Effects.

Для native render/effect plugins дополнительно:

- CPU;
- GPU;
- MFR;
- Smart Render;
- ROI;
- 8 bpc;
- 16 bpc;
- 32 bpc float;
- Linear Color workflow;
- применимые OCIO-конфигурации;
- extended-range float values;
- отсутствие непреднамеренного clipping.

Для scripts / panels дополнительно:

- UI;
- callbacks;
- events;
- timers;
- Undo / Redo;
- Undo Group safety;
- file operations;
- host calls;
- большие проекты;
- permissions;
- repeated execution.

Новая функция не считается готовой, если ломает существующее рабочее поведение.

---

## 10. Evidence

Утверждения:

- «исправлено»;
- «работает»;
- «ускорено»;
- «проблема устранена»;
- «регрессии нет»;
- «готово»

допускаются только при наличии подтверждения.

Evidence может быть:

- автоматический тест;
- integration test;
- реальный тест в After Effects;
- лог;
- benchmark;
- profiler;
- screenshot;
- video capture;
- сравнение output;
- hash;
- воспроизводимый результат.

Анализ кода сам по себе не считается доказательством исправления.

Компиляция без ошибок также сама по себе не является доказательством корректной работы.

---

## 11. Stop Criteria

Задача считается законченной только если:

1. Требование реализовано.
2. Artifact успешно создан.
3. Основной сценарий реально проверен.
4. Regression Level 1 пройден.
5. Нет известных критических ошибок.
6. Нет необъяснённых warnings/errors, относящихся к инструменту.
7. Документация обновлена.
8. Изменения зафиксированы в Git.
9. Есть Evidence результата.
10. Build / Artifact Identity известен.
11. Если задача performance-critical — есть реальные замеры.
12. Если это milestone / release / manual test — пройден Regression Level 2.
13. Проверен именно тот artifact, который планируется передавать пользователю.

Если хотя бы один обязательный пункт не выполнен — задача не считается завершённой.

---

## 12. Один источник истины

Код, Git, artifact, документация, статус проекта и результаты тестов не должны противоречить друг другу.

Источником подтверждённого состояния проекта является:

**проверенный Git commit + идентифицированный artifact + Evidence его проверки**

Документация должна описывать именно это состояние.

Нельзя писать «готово», если:

- изменения не находятся в Git;
- Git имеет незадокументированные изменения;
- код не протестирован;
- тестировался другой artifact;
- неизвестен Build ID;
- документация описывает другое состояние;
- Evidence относится к другой версии.

---

## 13. Не менять рабочую архитектуру без необходимости

Не переписывать рабочую архитектуру только потому, что другой вариант:

- красивее;
- современнее;
- моднее;
- теоретически «правильнее».

Архитектурное изменение допустимо, если есть доказанная причина:

- bug;
- limitation;
- performance bottleneck;
- incompatibility;
- security issue;
- проблема поддержки;
- невозможность дальнейшего развития;
- существенное упрощение;
- измеримая польза.

Рабочий код не должен становиться collateral damage рефакторинга.

---

## 14. Качество кода

Код должен быть:

- чистым;
- безопасным;
- быстрым;
- простым;
- минимально достаточным;
- понятным;
- тестируемым;
- диагностируемым;
- без лишней архитектуры;
- без dead code;
- без ненужных dependencies.

Простое рабочее решение предпочтительнее сложной архитектуры без доказанной пользы.

---

## 15. Никаких костылей без причины

Не использовать временные, хрупкие или «магические» решения без необходимости.

Если workaround действительно нужен:

- объяснить причину;
- зафиксировать его в документации;
- описать ограничение;
- указать правильное долгосрочное решение;
- при необходимости создать технический долг с явным статусом.

Workaround не должен незаметно превращаться в постоянную архитектуру.

---

## 16. Диагностируемость

Проблема не должна выглядеть как:

> «просто не работает».

Инструмент должен позволять быстро определить:

- какая версия запущена;
- какой Build ID используется;
- на каком этапе произошёл сбой;
- причину ошибки;
- входные условия ошибки.

Нужны, где применимо:

- понятные логи;
- понятные ошибки;
- diagnostics;
- Build Identity;
- crash information;
- timings;
- feature-specific debug information.

Для scripts / panels особенно важно диагностировать:

- exceptions;
- host API failures;
- отсутствующие layers/comps/files;
- permission problems;
- CEP/UXP bridge errors;
- event lifecycle;
- timers;
- asynchronous operations.

### Non-interactive Render Safety

Render/background code path не должен требовать взаимодействия с пользователем.

Запрещены во время:

- `PF_Cmd_RENDER`;
- background rendering;
- `aerender`;
- render farm execution;
- других non-interactive операций,

любые действия, которые требуют ответа пользователя:

- `alert`;
- `prompt`;
- modal dialogs;
- confirmation dialogs;
- interactive error windows.

Ошибка в таком режиме должна:

1. корректно возвращаться через соответствующий API;
2. записываться в лог;
3. завершать или пропускать операцию предсказуемым образом;
4. не блокировать процесс ожиданием пользовательского ввода.

Диагностический UI допустим только в интерактивном UI-контексте.

Debug-информация не должна заметно ухудшать production performance.

---

## 17. Производительность и корректность изображения — высокий приоритет

Производительность должна оцениваться по типу инструмента.

### Native render / effect plugins

Render и RAM Preview должны быть максимально быстрыми без ухудшения качества изображения.

Особое внимание:

- CPU;
- GPU;
- Multi-Frame Rendering;
- RAM;
- кэшированию;
- копированию кадров;
- allocations;
- многопоточности;
- Smart Render;
- ROI;
- CPU ↔ GPU transfers;
- bit depth;
- pixel format conversions.

### Color / Bit Depth Correctness

Render/effect plugin должен корректно работать во всех заявленных режимах:

- 8 bpc;
- 16 bpc;
- 32 bpc float.

Для 32 bpc:

- сохранять floating-point precision там, где это предусмотрено алгоритмом;
- корректно работать с Linear Color workflow;
- не предполагать, что входные значения всегда находятся в диапазоне `0.0–1.0`;
- не выполнять непреднамеренный clamp;
- не создавать clipping значений ниже `0.0` или выше `1.0`, если этого явно не требует алгоритм;
- корректно обрабатывать HDR / extended-range значения.

Если используется color management, проверять:

- project working space;
- linearized working space;
- применимые OCIO workflows;
- преобразования между color spaces;
- CPU/GPU parity после color conversions.

Результат эффекта не должен неожиданно меняться только из-за перехода между 8/16/32 bpc, кроме ожидаемых различий precision/диапазона.

### Scripts / panels / CEP / UXP

Особое внимание:

- время запуска;
- UI latency;
- main-thread blocking;
- количество обращений к After Effects host;
- batching операций;
- file I/O;
- parsing;
- serialization;
- memory;
- event listeners;
- timers;
- polling;
- IPC / bridge calls;
- обработка больших проектов;
- работа с большим количеством layers/items.

Инструмент не должен создавать ненужную постоянную нагрузку в idle-состоянии.

---

## 18. Оптимизация только по измерениям

Если оптимизация усложняет код, она должна быть подтверждена реальными замерами.

Не оптимизировать по принципу:

> «кажется, так быстрее».

Сравнивать результат с зафиксированным baseline.

Для каждого существенного performance-изменения желательно иметь:

**before → change → after**

Оптимизация без измеримого улучшения не должна усложнять production-код.

---

## 19. Profiling — два уровня

### Level 1 — во время разработки

После performance-sensitive изменений:

- быстрый benchmark;
- проверка очевидных regressions;
- сравнение с baseline.

### Level 2 — перед milestone / release / ручным тестом

Проводить profiling реального сценария внутри After Effects.

### Для native render/effect plugins

Проверять:

- CPU;
- GPU;
- RAM;
- Render;
- RAM Preview;
- allocations;
- threading;
- MFR;
- transfers;
- Smart Render;
- ROI;
- pixel-format conversions;
- bottlenecks.

### Для scripts / panels / extensions

Проверять:

- startup time;
- execution time;
- UI responsiveness;
- main-thread stalls;
- host calls;
- file I/O;
- memory;
- event listeners;
- timers;
- polling;
- repeated operations;
- большие проекты;
- bottlenecks.

Теоретического анализа недостаточно.

Performance-critical вывод должен подтверждаться реальным profiling или benchmark.

---

## 20. Воспроизводимые сборки и artifacts

Один и тот же исходный код должен предсказуемо создавать один и тот же функциональный production artifact на чистой системе.

Не должно быть скрытой зависимости от:

- старых локальных файлов;
- старых SDK;
- старых Node/npm dependencies;
- глобальных packages;
- кэшей;
- настроек машины;
- случайных environment variables;
- предыдущих builds;
- вручную изменённых production-файлов.

Dependencies должны быть:

- явно определены;
- versioned/pinned там, где это разумно;
- воспроизводимо устанавливаемы.

Production artifact не должен зависеть от случайного состояния машины разработчика.

---

## 21. Совместимость

Вести матрицу реально проверенной совместимости.

Учитывать, где применимо:

- версии After Effects;
- macOS;
- Windows;
- Apple Silicon;
- Intel;
- GPU;
- CPU/GPU render path;
- ExtendScript;
- ScriptUI;
- CEP;
- UXP;
- runtime/framework versions;
- permissions;
- файловые пути;
- special/unicode characters;
- локализацию;
- 8/16/32 bpc;
- Linear Color;
- OCIO.

### UXP Sandbox / Permissions

UXP нельзя считать эквивалентом ExtendScript или CEP по доступу к файловой системе.

Для UXP отдельно проверять:

- filesystem sandbox;
- `localFileSystem` API;
- manifest permissions;
- user-granted file/folder access;
- persistence предоставленных file/folder tokens;
- поведение после restart;
- отсутствие разрешения;
- отозванное или недействительное разрешение;
- попытку доступа к файлу вне разрешённой области.

Код не должен предполагать наличие произвольного доступа к файловой системе.

Отказ в доступе должен обрабатываться как штатная ситуация, а не как необъяснимый crash.

Не считать платформу, runtime или конфигурацию поддерживаемой, пока она реально не проверена.

Если что-то не проверено — помечать как `untested`, а не как `supported`.

## 22. Дополнительные проверки для Scripts / Panels / Tools

Для script / ScriptUI / CEP / UXP инструментов дополнительно проверять:

### Lifecycle

- первый запуск;
- повторный запуск;
- закрытие;
- повторное открытие;
- restart After Effects;
- reload extension;
- восстановление состояния.

### UI

- responsiveness;
- resize;
- scaling;
- HiDPI / Retina;
- разные размеры панели;
- отсутствие зависания интерфейса;
- отсутствие accidental double-actions.

### After Effects Integration

Проверять:

- корректный active project;
- отсутствие project;
- отсутствие composition;
- отсутствие selection;
- неправильный тип selection;
- удалённые layers/items;
- locked layers;
- missing footage/files;
- Undo / Redo;
- отмену операции пользователем.

### Undo Safety

Любая операция, использующая:

`app.beginUndoGroup()`

должна быть спроектирована так, чтобы соответствующий:

`app.endUndoGroup()`

гарантированно выполнялся даже при exception или досрочном выходе из операции.

Для сложных операций использовать структуру:

`try ... finally`

так, чтобы закрытие Undo Group находилось в `finally`.

Ошибка внутри операции не должна оставлять неконтролируемое состояние Undo transaction.

Дополнительно проверять:

- exception внутри Undo Group;
- early return;
- пользовательскую отмену;
- повторный запуск после ошибки;
- Undo;
- Redo;
- несколько последовательных операций.

### State

- preferences;
- saved state;
- corrupted state;
- migration старых настроек;
- reset state.

### Repeated Execution

Одна и та же операция должна корректно работать:

- первый раз;
- второй раз;
- много раз подряд.

Она не должна оставлять:

- duplicate listeners;
- duplicate UI;
- zombie state;
- лишние timers;
- лишние background processes.

### File System

Проверять:

- отсутствующие файлы;
- read-only locations;
- permissions;
- длинные пути;
- пробелы;
- Unicode;
- кириллицу;
- специальные символы.

Для UXP дополнительно проверять:

- sandbox restrictions;
- `localFileSystem`;
- user-granted access;
- invalid/stale entries;
- отсутствие необходимого permission;
- отказ пользователя предоставить доступ.

## 23. Дополнительные проверки Native Effects / Render Plugins

Для native effect/render plugins дополнительно проверять:

### Render Context

- обычный interactive render;
- RAM Preview;
- export/render queue;
- `aerender`;
- background rendering;
- MFR;
- Smart Render, если поддерживается.

Ни один render code path не должен:

- открывать modal UI;
- требовать подтверждения пользователя;
- ждать interactive input;
- зависеть от наличия UI.

### Pixel Correctness

Проверять:

- 8 bpc;
- 16 bpc;
- 32 bpc float;
- alpha;
- premultiplied/unpremultiplied сценарии, где применимо;
- extreme values;
- negative float values;
- float values выше `1.0`;
- отсутствие unintended clipping;
- отсутствие unintended quantization.

### Color Management

Проверять, где применимо:

- Working Space;
- Linear Working Space;
- OCIO;
- HDR / extended range;
- CPU/GPU consistency.

### CPU / GPU Parity

Если эффект имеет CPU и GPU implementation, визуальный результат должен совпадать в пределах заранее определённой допустимой погрешности.

Расхождения должны измеряться, а не оцениваться только визуально.

## 26. Перед ручным тестом пользователя

Сначала выполнить все разумные автоматические проверки.

Все обнаруженные ошибки должны быть:

1. исследованы;
2. исправлены;
3. повторно проверены.

Нельзя передавать пользователю artifact с упавшими обязательными проверками.

После успешных автоматических проверок пройти финальный checklist.

### Финальный Checklist

1. Проверка Git state.
2. Проверка Build / Artifact Identity.
3. Clean Build / Clean Package.
4. SHA-256 production artifact.
5. Удаление старых версий.
6. Чистая установка production artifact.
7. Code Audit.
8. Refactoring при необходимости.
9. Debugging.
10. Automated Smoke / Integration Tests.
11. Regression Level 2.
12. Profiling.
13. Optimization при наличии доказанного bottleneck.
14. Deep Performance Audit для performance-critical инструмента.
15. Реальное тестирование внутри After Effects.
16. Проверка логов и ошибок.
17. Проверка Undo Safety, если применимо.
18. Проверка UXP/CEP permissions, если применимо.
19. Проверка non-interactive render/aerender, если применимо.
20. Проверка 8/16/32 bpc и color management для render/effect plugins.
21. Проверка документации.
22. Проверка Evidence.
23. Проверка совместимости, относящейся к текущему milestone.
24. Финальная проверка установленного/загруженного production artifact.
25. Проверка, что реально запущенный Build ID соответствует проверенному artifact.

Только после этого передавать artifact пользователю.

# Главное правило

**Пользователь — последний этап QA, а не инструмент диагностики.**

**Перед передачей пользователю разработчик обязан доказать, что передаёт именно проверенный текущий production artifact.**

До ручного теста должны быть исчерпаны все разумные автоматические и технические способы проверки.

Пользователь не должен обнаруживать проблемы, которые могли быть найдены:

- автоматически;
- через логи;
- через static analysis;
- через profiling;
- через regression testing;
- через clean testing;
- через automated After Effects testing;
- через нормальную инженерную проверку.

Ручной тест пользователя нужен для подтверждения поведения в его реальной среде, а не для поиска ошибок, которые могла найти система разработки.
