
# Development Rules

## 1. Перед каждым шагом

Перед началом любого этапа разработки сверяться с этим документом.

---

## 2. Чистое тестирование

Каждый финальный, regression- и bug-reproduction тест в After Effects должен запускаться с чистого состояния:

- без старых сборок;
- без кэшей;
- без временных файлов;
- без следов предыдущих тестов.

Новый тест не должен случайно использовать что-то старое.

Для быстрых внутренних итераций допускается сокращённый цикл, если это не влияет на достоверность результата.

---

## 3. Research перед разработкой

Перед написанием новой функции сначала проверить:

- Adobe SDK и документацию;
- существующие решения;
- open-source;
- похожие плагины;
- готовые проверенные подходы.

Если хорошее решение уже существует — адаптировать его, а не писать заново.

---

## 4. Максимальная автоматизация

Всё, что можно сделать без участия пользователя, делать автоматически.

Не просить пользователя:

- запускать проверки;
- собирать данные;
- тестировать;
- выполнять технические операции,

если это можно сделать самостоятельно.

---

## 5. Максимальная скорость разработки

Всё независимое, что можно безопасно выполнять параллельно, выполнять параллельно:

- research;
- сборки;
- тесты;
- аудит;
- profiling;
- документацию.

Параллельность не должна снижать достоверность тестирования или создавать race conditions между этапами.

---

## 6. Git обязателен

Любое изменение проходит через Git.

Каждый законченный этап:

- отдельное понятное изменение;
- понятный commit;
- возможность быстро откатиться.

Не смешивать несвязанные изменения в одном commit без необходимости.

---

## 7. Build Identity

Для каждой тестируемой сборки должно быть однозначно известно:

**commit → исходный код → build → `.plugin/.aex` → установленный файл → запущенная версия в After Effects**

Нельзя тестировать сборку, если невозможно доказать, из какого commit она собрана.

Перед ручным тестом пользователя обязательно убедиться, что:

- собран нужный commit;
- старые версии удалены;
- установлен именно новый binary;
- After Effects загрузил именно его;
- версия сборки однозначно идентифицируется.


Практический лайфхак для внедрения Build Identity
Чтобы проверка Build Identity в After Effects занимала 1 секунду и не требовала ручных манипуляций, зашейте автоматическую проброску Git-хэша в бинарник на этапе сборки:

В CMake / MSBuild / Xcode: Автоматически передавайте тег/хэш текущего коммита через дефайны компилятора

В коде плагина: Выводите эти переменные:
В окне PF_Cmd_ABOUT (когда пользователь или вы кликаете на About... у плагина в панелях AE).
В первую строчку при инициализации лог-файла плагина.


---

## 8. Baseline перед изменениями

Перед серьёзной правкой фиксировать текущее состояние:

- что работает;
- что не работает;
- скорость;
- память;
- Render performance;
- RAM Preview performance;
- известные ошибки;
- текущую сборку и commit.

Это точка сравнения после изменений.

---

## 9. Regression check — два уровня

### Level 1 — после каждого commit

Выполнять быстрые проверки:

- build;
- основные функции;
- отсутствие очевидных regressions;
- smoke tests;
- базовые performance sanity checks.

### Level 2 — перед milestone / release / ручным тестом пользователя

Проводить полный regression:

- весь основной функционал;
- edge cases;
- performance;
- память;
- CPU/GPU;
- MFR;
- совместимость;
- реальные тесты внутри After Effects.

Новая функция не считается готовой, если она ломает существующее рабочее поведение.

---

## 10. Evidence

Утверждения:

- «исправлено»;
- «работает»;
- «ускорено»;
- «проблема устранена»;
- «регрессии нет»

допускаются только при наличии подтверждения.

Подтверждением могут быть:

- автоматический тест;
- реальный тест в After Effects;
- лог;
- benchmark;
- profiler;
- screenshot;
- сравнение output;
- воспроизводимый результат.

Анализ кода сам по себе не считается доказательством исправления.

---

## 11. Stop Criteria

Задача считается законченной только если:

1. Требование реализовано.
2. Код собирается.
3. Основной сценарий проверен.
4. Regression Level 1 пройден.
5. Нет известных критических ошибок.
6. Нет необъяснённых warnings/errors.
7. Документация обновлена.
8. Изменения зафиксированы в Git.
9. Есть Evidence результата.
10. Если задача performance-критичная — есть реальные замеры.
11. Если это milestone/release/manual test — пройден Regression Level 2.
12. Известно, какая именно сборка была проверена.

Если хотя бы один обязательный пункт не выполнен — задача не считается завершённой.

---

## 12. Один источник истины

Код, Git, документация, статус проекта и реальные результаты тестов не должны противоречить друг другу.

Источником текущего состояния проекта является проверенный Git commit.

Документация должна описывать именно текущее состояние этого commit.

Нельзя писать в статусе «готово», если:

- изменения не находятся в Git;
- они не протестированы;
- тестировалась другая сборка;
- документация описывает другое состояние.

---

## 13. Не менять рабочую архитектуру без необходимости

Не переписывать рабочую архитектуру только потому, что другой вариант кажется красивее или современнее.

Архитектурное изменение допустимо, если есть доказанная причина:

- bug;
- limitation;
- performance bottleneck;
- incompatibility;
- security issue;
- невозможность дальнейшего развития;
- существенное упрощение с измеримой пользой.

Рабочий код не должен становиться collateral damage рефакторинга.

---

## 14. Качество кода

Код должен быть:

- чистым;
- безопасным;
- быстрым;
- простым;
- минимально достаточным;
- понятным;
- тестируемым;
- без лишней архитектуры;
- без dead code.

---

## 15. Никаких костылей без причины

Не использовать временные или «магические» решения без необходимости.

Если workaround действительно нужен:

- объяснить причину;
- зафиксировать его в документации;
- указать правильное долгосрочное решение.

---

## 16. Диагностируемость

Проблема не должна выглядеть как «просто не работает».

Нужны:

- понятные логи;
- понятные ошибки;
- возможность быстро определить причину сбоя;
- возможность определить загруженную версию плагина.

---

## 17. Производительность — высокий приоритет

Render и RAM Preview должны быть максимально быстрыми без ухудшения качества изображения.

Особое внимание:

- CPU;
- GPU;
- Multi-Frame Rendering;
- RAM;
- кэшированию;
- копированию кадров;
- allocations;
- многопоточности;
- Smart Render;
- ROI;
- CPU ↔ GPU transfers.

---

## 18. Оптимизация только по измерениям

Если оптимизация усложняет код, она должна быть подтверждена реальными замерами.

Не оптимизировать по принципу:

> «кажется, так быстрее».

Сравнивать результаты с зафиксированным baseline.

---

## 19. Profiling — два уровня

### Level 1 — во время разработки

После performance-sensitive изменений:

- быстрый benchmark;
- проверка очевидных regressions;
- сравнение с baseline.

### Level 2 — перед milestone / release / ручным тестом

Обязательное реальное profiling внутри After Effects:

- CPU;
- GPU;
- RAM;
- Render;
- RAM Preview;
- allocations;
- threading;
- MFR;
- transfers;
- bottlenecks.

Теоретического анализа недостаточно.

---

## 20. Воспроизводимые сборки

Один и тот же исходный код должен собираться предсказуемо на чистой системе.

Не должно быть скрытой зависимости от:

- старых локальных файлов;
- старых SDK;
- кэшей;
- настроек машины;
- случайных environment variables;
- предыдущих builds.

---

## 21. Совместимость

Вести матрицу реально проверенной совместимости:

- версии After Effects;
- macOS;
- Windows;
- Apple Silicon;
- Intel;
- GPU.

Не считать платформу поддерживаемой, пока она реально не проверена.

---

## 22. Документация после каждого этапа

После каждого законченного шага обновлять:

- статус;
- архитектуру;
- реализованные функции;
- ограничения;
- тесты;
- принятые решения;
- известные проблемы;
- build / commit;
- следующие шаги.

Документация должна соответствовать текущему коду.

---

## 23. Итоговая техническая документация

После завершения проекта сохранить:

- как всё устроено;
- какие API использованы;
- какие решения сработали;
- какие не сработали;
- проблемы After Effects;
- найденные performance-паттерны;
- способы диагностики;
- известные ограничения;
- полезные решения для будущих AE-проектов.

Проект должен оставлять после себя инженерную базу знаний.

---

## 24. Перед ручным тестом пользователя

Сначала определить, можно ли проверить всё автоматически.

Если можно — проверить автоматически.

Если нельзя, перед передачей пользователю пройти:

1. Проверку Build Identity
2. Clean Build
3. Code Audit
4. Refactoring при необходимости
5. Debugging
6. Profiling
7. Optimization
8. Deep Performance Audit
9. Реальное profiling внутри After Effects
10. Regression Level 2
11. Проверку логов и ошибок
12. Проверку документации
13. Проверку Evidence
14. Финальную проверку установленного `.plugin/.aex`

Только после этого передавать сборку пользователю.

---

## 25. Общение с пользователем

Общаться:

- коротко;
- человеческим языком;
- без лишних технических деталей;
- без воды;
- без перегрузки информацией.

Технические подробности давать только когда они действительно нужны.

Не утверждать «готово» или «исправлено» без Evidence.

---

# Главное правило

**Пользователь — последний этап QA, а не инструмент диагностики.**

**Перед передачей пользователю разработчик обязан доказать, что передаёт именно проверенную текущую сборку.**

До ручного теста должны быть исчерпаны все разумные автоматические и технические способы проверки.

Пользователь не должен обнаруживать проблемы, которые могли быть найдены автоматически, через логи, profiling, regression testing или нормальную инженерную проверку.
